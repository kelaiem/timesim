## §338 — A native battery: one deterministic library, WebAssembly kernels, identical results on ARM and x86 — PARTIAL: landing 0's check profile and landing 1 (the native host) shipped

Proposed 2026-11-07 by the owner: a battery that is not platform or runtime dependent, gives identical results on ARM
and x86, is optimized for runtime efficiency, and targets WebAssembly. The design (one JS library of the build and the
checks, a compiled C++ kernel to wasm for the collision queries, hosts around it, and a byte-identical report across
architectures and engines as the gate) is the roadmap entry. This file records what has shipped.

### Landing 0, in part: where the check time goes, by function

`tools/probe-338-check-profile.mjs` boots the way the battery does (`virginBoot` + `prepPage`) and runs named tasks (a
check, or a §127 `check:axis` slice) under a CDP sampling profile started after boot: time by source file, the top
functions by self and by inclusive time, and a `.cpuprofile` per task. Nothing had profiled the CHECK phase by function:
§108's census times tiers, and §239's profile is the boot.

Eight heavy tasks (the heaviest slice of each sliced sweep, plus `sweptOverlap`, `penetration`, `plateSeats`,
`intraUnit`; about 40% of the `COSTS` column), dev container, 4 vCPU, 1 ms sampling, 380.5 s sampled, full coverage:

| inclusive, all eight | share |
|---|---|
| BVH closest-point query (`closestPointToGeometry`) | 55.3% |
| boolean triangle–triangle intersection (`intersectsGeometry`) | 22.4% |
| BVH construction (`MeshBVH`) | 5.5% |
| `sampledVerdict` | 4.0% |
| `setPose` | 3.4% |
| `updateMatrixWorld` | 1.5% |
| parity raycast | 1.2% |

The hottest leaves are three-mesh-bvh's segment–segment distance (22.6% together), three's
`Triangle.closestPointToPoint` (11.9%), `distanceToBox` (7.8%) and the separating-axis triangle's setup (5.8%).
`inspect.js` is 2–16% of a task. So the kernel's first primitive is the BVH-vs-BVH closest-point query, its second the
boolean intersection, and the two with BVH construction are the 83% a compiled kernel can address.

### Landing 1: the native host

**The plan was to cut a `src/movement.js` out of `main.js`. The measurement made that unnecessary for this landing,
and the landing is smaller and safer for it.** Booting `main.js` UNCHANGED in Node with crude page stand-ins, the
first thing that broke was line 48,774 of 66,104: the service-worker registration, after every part is cut. The
build region's browser references are about two. So the host answers the page's questions and the build runs as
written; `main.js` is not touched, so its browser build cannot have moved.

**What shipped.**

- `src/spec-fields.js`: the §22/§161 spec roster (`SPEC_FIELDS`) with `readSpec` and `publishSpec`, moved out of
  index.html's inline classic script, the one host fact the build needs and the one place a non-page host could not
  read. `src/spec-boot.js` publishes it for the page and is the entry module's FIRST import (dependencies evaluate in
  import order, so `layout.js`, which reads `__WATCH_SPEC` at import time, still sees it). It is a NAMED import on
  purpose: `tools/stamp-release.mjs` versions `from '…'` and `import('…')` specifiers and would ship a bare
  `import '…'` unstamped. `publishSpec` was held equal to the inline script's globals on four queries (none, two
  numbers, every string-parsed knob at once, an unknown key).
- `tools/native/`: `host.mjs` (`installHost`/`bootNative`: the DOM as one forgiving element, the battery's loopback
  origin so `state.js` takes `virginBoot`'s 404 `/__state` path, `fetch` answering 404 for `/__state` and
  `version.json` and THROWING for anything else, no animation frames, the spec through `publishSpec`, and a `touched`
  count of every stand-in a boot exercised), `three-headless.mjs` (the vendored three with a renderer and a PMREM
  that draw nothing), `loader.mjs`, and `boot.mjs` (boot one spec, print its wall, warnings, stand-ins and
  fingerprint). The host lives under `tools/`, so the app stays dependency-free and the payload does not carry it.
- `tools/probe-338-native-boot.mjs` and `.github/workflows/native-host.yml`: Chromium and native boots of the identity
  and `arrangement=designed`, in parallel (~75 s).

**Measured (the probe, this container: Node 22.23.4 / V8 12.4 against Chrome for Testing 153 / V8 15.3).**

| | identity | `arrangement=designed` |
|---|---|---|
| boots silent, both hosts | yes | yes |
| one roster (33 keys) and one parsed spec | yes | yes |
| §52 fingerprint | 556372915 = 556372915 | 512616833 = 512616833 |
| §152 PLACE digest, 66 units × 52 poses | identical | identical |
| §152 SHAPE digest | 27 of 66 differ | 27 of 66 differ |

The control holds: the native identity build's fingerprint differs from Chromium's designed build, so the comparison
can fail and the spec reaches each build. A native boot takes ~27 s here.

**SHAPE is reported, not gated, and the reason is the landing's main finding.** Each differing unit is classified at
the digest poses:

- *index-order* (15 units): positions and the triangle SET agree; only the index buffer's order differs. The page's
  first frames build bounds trees (103 on the identity build), and three-mesh-bvh reorders a geometry's index in
  place. So §152's SHAPE digest, which hashes the live index, is a function of what the page did after boot as well
  as of the metal. It reproduces across two browser boots (§152's gate) because both run the same frames.
- *positions* (11): the same vertex count, a few coordinates differing by ~1e-17, values near zero from a
  transcendental.
- *topology* (1 on identity, 3 on designed): a mesh's VERTEX COUNT differs: `Alarm winding arrest` mesh #24, 31090
  in Chromium against 31102 native; on the designed build also `Alarm release crank` and `Dial` mesh #176, 554
  against 548. A construction decision flips on a last-ulp difference. The fingerprint, which reads quantized boxes,
  cannot see it.

The cause of the last two classes is the ENGINE, not the host. On 20,000 inputs, V8 12.4 and V8 15.3 disagree by 1 ulp
on 2–11% of inputs for every transcendental (`sin`, `cos`, `tan`, `atan`, `atan2`, `exp`, `log`, `pow`, `**`, `cbrt`,
…); `hypot` agrees between the two V8s and not with JavaScriptCore; only `sqrt`, which IEEE 754 requires to be
correctly rounded, agrees everywhere. V8 15.3 is much closer to
JavaScriptCore (Bun 1.4.4) than to V8 12.4, so V8 changed its maths library between those versions. "The same engine
gives the same results" is therefore false across engine VERSIONS, which is also what the `ci-env-upgrade` skill's
"same source builds different metal on a new browser" describes. A report leaf-identical between the hosts (§338's
G2) cannot hold until the build's arithmetic stops depending on the engine's libm: §338's deterministic-math landing
now comes before the native runner's parity gate, not after it.

**Not done here, and filed in the entry:** the native battery runner (landing 2), deterministic maths and the `**`
