## §338 — A native battery: one deterministic library, WebAssembly kernels, identical results on ARM and x86 — PARTIAL: landing 0's check profile, landing 1 (the native host), landing 2 (deterministic maths), landing 3 (the native battery), landing 4 (the pose-conditioning guard), landing 5 (the compiled kernel's first primitive), landing 6 (its second, the boolean intersection), landing 7 (exact contact), landing 8 (exact primitives in every mode) and landing 9 (a morphing mesh's tree refitted) shipped

Proposed 2026-11-07 by the owner: a battery that is not platform or runtime dependent, gives identical results on ARM
and x86, is optimized for runtime efficiency, and targets WebAssembly. The design (one JS library of the build and the
checks, a compiled C++ kernel to wasm for the collision queries, hosts around it, and a byte-identical report across
architectures and engines as the gate) is the roadmap entry. This file records what has shipped.

**SHAPE is reported, not gated, and the reason is the landing's main finding.** Each differing unit is classified at
the digest poses:

- *index-order* (15 units): positions and the triangle SET agree; only the index buffer's order differs. The page's
  first frames build bounds trees (103 on the identity build), and three-mesh-bvh reorders a geometry's index in
  place. So §152's SHAPE digest, which hashes the live index, is a function of what the page did after boot as well
  as of the metal. It reproduces across two browser boots (§152's gate) because both run the same frames.
- *positions* (11): the same vertex count, a few coordinates differing by ~1e-17, values near zero from a
  transcendental.
- *topology* (1 on identity, 3 on designed): a mesh's VERTEX COUNT differs: `Alarm winding arrest` mesh #24, 31090
  in Chromium against 31102 native; on the designed build also `Alarm release crank` and `Dial` mesh #176, 554
  against 548. A construction decision flips on a last-ulp difference. The fingerprint, which reads quantized boxes,
  cannot see it.

The cause of the last two classes is the ENGINE, not the host. On 20,000 inputs, V8 12.4 and V8 15.3 disagree by 1 ulp
on 2–11% of inputs for every transcendental (`sin`, `cos`, `tan`, `atan`, `atan2`, `exp`, `log`, `pow`, `**`, `cbrt`,
…); `hypot` agrees between the two V8s and not with JavaScriptCore; only `sqrt`, which IEEE 754 requires to be
correctly rounded, agrees everywhere. V8 15.3 is much closer to
JavaScriptCore (Bun 1.4.4) than to V8 12.4, so V8 changed its maths library between those versions. "The same engine
gives the same results" is therefore false across engine VERSIONS, which is also what the `ci-env-upgrade` skill's
"same source builds different metal on a new browser" describes. A report leaf-identical between the hosts (§338's
G2) cannot hold until the build's arithmetic stops depending on the engine's libm: §338's deterministic-math landing
now comes before the native runner's parity gate, not after it.

**Not done in landing 1, and filed in the entry:** deterministic maths, the canonical SHAPE digest and the ARM legs
(landing 2, below), the native battery runner, and the wasm kernel.

### Landing 2: deterministic maths

**The goal: the same metal from the same source on every engine and CPU.** ECMA-262 leaves every transcendental
`Math` function "implementation-approximated", and landing 1 measured what that costs. The fix is to stop asking
the engine.

**What shipped.**

- `vendor/det-math.module.js` and `vendor/LICENSE-stdlib.txt`, GENERATED by `tools/det-math-vendor.mjs` from exactly
  pinned stdlib-js packages (pure-JavaScript ports of FreeBSD msun / Sun fdlibm, Apache-2.0, the Sun notices kept)
  bundled by a pinned esbuild. `--check` rebuilds it in a temporary directory and compares bytes: 201,748 of them,
  reproduced. The tool asserts the bundle calls no `Math` builtin but the exact ones (`abs`, `ceil`, `floor`, `round`,
  `sqrt`) and uses no `**`. Measured before choosing it: on 40,000 inputs per function, its results are bit-identical
  in V8 12.4, V8 15.3 and JavaScriptCore; it is within 2 ulp of V8's own; and it costs 1.05–2.2× a builtin call
  (`sin` 1.84×, `cos` 1.08×, `atan2` 1.05×, `pow` 2.22×), which the boot does not notice (native boot 25.5 s against
  27–28 s before).
- `src/det-math.js`: `installDetMath` replaces the 22 implementation-approximated functions (`sin` … `atanh`, `pow`,
  `hypot`) on `Math`. The exact ones stay the engine's, because IEEE 754 or ECMA-262 already fixes every bit of them.
  Two functions are written here rather than taken from stdlib:
  - **`pow` applies ECMA-262's Number::exponentiate itself** and gives stdlib only a finite positive base. Measured,
    stdlib follows C at the special values and is wrong at several: `pow(NaN, 0)` gives NaN (JS requires 1),
    `pow(±1, ±Infinity)` gives 1 (JS requires NaN), the ±0 and −Infinity bases are off, and its odd-integer test reads
    `y − 1`, so `pow(-1, 1e300)` gave −1.
  - **`hypot`** is ECMA-262's variadic function, computed as m·√Σ(xᵢ/m)², each operation correctly rounded.

  Every special value now matches the engine's, which the spec pins down. What is left is accuracy at the extremes,
  where the true value lies next to a boundary: `exp(-745)` underflows one subnormal early, `cosh(710)` overflows,
  and `pow` differs by 1 ulp near 1. All of it is deterministic, and none of it is in the build's domain.
- `src/det-math-boot.js` installs it and checks its KNOWN ANSWERS: per function, a hash of the result bits (NaN made
  one pattern) over a fixed input set, recorded in `src/det-math-kat.js` by `tools/det-math-kat.mjs`. It is
  **index.html's first import**, so every later module, three.js included, computes with it. The native host imports
  it before `main.js`. `main.js` re-says its findings as boot warnings (rule 6), and warns when no host installed it.
- **The `**` operator** cannot be reached by replacing `Math.pow`, so the build no longer uses it.
  `tools/check-det-math.mjs --fix` rewrote 313 sites on index.html's module graph, re-run after rebasing onto #921 (228 in `main.js`, and the 2 in
#921's new `src/ribbon-solve.js`, which the lint found the day it joined the graph) from the
  AST as `Math.pow`. Without `--fix` it gates:
  - the graph free of `**`, except two named vendored sites that are exact (`Infinity ** 2`, `2 ** 16`); an allowed
    site that disappears is stale and fails;
  - the bundle's audit;
  - the entry's first import;
  - the full known answers.

  Its controls plant a `**` and a `Math.sin` and require both to be seen.
- **§152's SHAPE digest hashes the index as a triangle SET** (`indexSetHash`: each triangle rotated to its smallest
  index, which keeps its winding, then hashed; per-triangle hashes summed under two mixes). Landing 1 found that the
  page's first frames build bounds trees that permute index buffers in place, so the key carried which trees had been
  built. This changes every stored key once, which sends the next incremental run whole: the safe direction.
- **`native-host.yml` is the portability gate**, in three jobs:
  - `maths`: the vendored bytes, the lint, and the known answers on Node (V8) and Bun (JavaScriptCore);
  - `native-host`: the probe on `ubuntu-latest` (x64) AND `ubuntu-24.04-arm` (arm64), SHAPE gated, each writing its
    digests;
  - `cross-arch`: `tools/compare-338-hosts.mjs`, every build on both machines one movement, unit digest for unit
    digest, with a control.
- The deploys assert `LICENSE-stdlib.txt` beside the bundle, and `tools/` gains one pinned package (`acorn`, the
  parser the lint and the codemod use).

**Measured (`tools/probe-338-native-boot.mjs`, this container: Node 22.23.4 / V8 12.4 against Chrome 153 / V8 15.3).**

### Landing 4: the pose-conditioning guard

**The question.** #921 found the Balance's metal 1.28e-9 apart between two V8 versions at one pose of §152's
net, the fingerprint's held wind `{tau 0.13, …, maintHold 0.5}`, enough to straddle a PLACE cell edge. Landing 2
made that pose hash equal across hosts, because bit-identical arithmetic leaves nothing to amplify. That leaves
everything that is not bit-identical (a page or tool the maths does not cover, a re-recorded maths library, an
engine or compiled kernel that breaks IEEE) one steep pose away from a report difference that says nothing about
the watch. Landing 3 made report parity a CI gate, so the guard comes next.

**What it measures.** `tools/probe-338-pose-conditioning.mjs` boots the tree in worker threads, each its own native
host. Two boots use the tree's own maths, and one per seed uses a SYNTHETIC ENGINE: every implementation-approximated
`Math` function (det-math's 20, plus `pow` and `hypot`) answers one ulp off, up or down, on about one input in eight,
by a hash of the input's bits. That is the measured shape of V8 12.4 against V8 15.3. Values ECMA-262 fixes exactly
are left alone, because every engine agrees on them. The engine is installed BEFORE `main.js` evaluates. Injected
only while posing, it moved nothing at all, on this tree and on #921's: #921's τ came from boot constants. At every
digest pose, every mesh's world matrix is compared, element by element.

**The bound, derived.** A host difference Δ in a matrix element straddles a PLACE cell edge with probability about
Δ·Q (Q = `DIGEST_PLACE_Q` = 1e6). Keeping the net's expected straddles under one needs every element under
1 / (Q · poses · meshes · 16) = 1 / (1e6 · 52 · 823 · 16) = **1.46e-12**. The mesh count is every mesh in the scene,
a superset of the digest's units, so the bound is the stricter for it.

**Measured, before the fix** (seed 1, against the tree's own maths):

| tree | worst pose | Δ metal | Δτ | every other pose |
|---|---|---|---|---|
| #921's (`c40712dd`, engine maths) | the held wind, maintHold 0.5 | 6.7e-10 (Balance) | 1.4e-12 s | ≤ 2.8e-14 |
| `main` at landing 3 (deterministic maths) | the held wind, maintHold 0.5 | 1.95e-9 (Balance) | 4.0e-12 s | ≤ 3.6e-14 |

The probe reproduces #921's finding: the same pose and the same unit, at the same order of magnitude (#921: 2.6e-12 s,
1.28e-9). The defect was latent on `main`, five orders over every other pose and 1,300 times over the bound. It hid
because two hosts with landing 2's maths have no last-ulp difference to amplify.

**The cause.** `MAINT_HOLD.tauAt` poses a hold by inverting the GREAT WHEEL's angle: the largest τ whose advance does
not pass h·(run − recoil). The wheel turns about once an hour, so a last-ulp difference in its angle (in any boot
constant `barrelMeshAngle` reads) reaches τ multiplied by 1/ω. The balance then stands 4e-12 s later in its swing.
This is the inversion of a slow function, not a step edge. Every h is exposed, by how far its target falls from a
fast stretch of the train.

**The fix (#921's shape a, measured by shape b).** A hold short of the stop is posed at the last EXTREME of the
balance at or before that τ, `MAINT_HOLD.restAtOrBefore`. The extremes are (τ − `BALANCE_PHASE_TAU`)·2F = k + ½,
`balanceTheta`'s own turning points: the fork banked, the wheel locked, the balance at rest. There a shift of τ moves
no metal to first order, and k is an integer that a 1e-12 shift does not reach unless τ lands within 1e-12 of a half
beat. The wheel there has advanced no further than the target, because the train is locked between the rest and τ.
The hold is never posed earlier than the drive-off, τ0, which is a literal. The STOP (h = 1) is not snapped: τ_stop
is where the pin meets the flank, a place. It is measured under the bound as it stands.
`maintHoldLaw.advanceTau` exposes the unsnapped inverse for the probe's control. The held poses move back by under a
half-beat: 850.405 → 850.308 s at h 0.5, 868.411 → 868.308 s at the axis's 24/47.

**Gates**, each with a control:
- determinism: two boots on the tree's own maths agree EXACTLY at every pose;
- the engine is live: tens of millions of results one ulp off at boot, and every pose moved at all;
- CONTROL: the held wind posed at the inverted τ reads over the bound. Seeds 1 and 2: 1.95e-9 and 1.68e-10, the
  Balance;
- every digest pose under the bound. Seeds 1 and 2: worst 3.55e-14 and 3.56e-13, four times under at the
  closest.

Restoring the unsnapped law turns the last gate red at the held wind (1.95e-9), which is the guard firing on the
defect it exists for. It runs on both architectures in `native-host.yml`, in about a minute.

**What the fix moved in the battery** (native, 4 workers, `report-diff` against `main`): 35/35 gates on both trees,
and 50 of 175,640 leaves.
- The EXPECTED escape wheel ⇄ pallet fork pair now touches at 26 of the 49 held poses instead of 20, because every
  held pose stands where a tooth is locked on a stone.
- Three `meshPhase` rows name a different worst pose, one reading 0.206% instead of 0.182% against a 2% bar.
- `plateSeats` tested 1,623 pairs instead of 1,676.

### The boot's warnings end where the build ends (harness, after landing 5)

`probe-338-native-boot`'s Chromium leg failed two unrelated PRs (#935, then #936) with one undeclared warn: "§38/TODO
8: the alarm's coincidence was crossed in ONE tick (1.7952 rad)". #935's next push passed with the same warn set. The
cause was the harness, not the PRs. `main.js` collects every `console.warn` for the life of the page in one buffer,
`__clock.bootWarns`. The live loop starts on the module's last line (`requestAnimationFrame(frame)`), and a page keeps
running frames until a harness takes its sweep hold. Under CI load (Chromium booting beside three native boots on 4
vCPUs), a starved frame could reach tick's runtime guard in that gap and read as a BOOT warn. BUILT §234 and §328
record the same guard firing under load on unchanged `main`.

**The fix is a boundary, not a filter.**
- `main.js` records the buffer's length on its last line.
- `__clock.buildWarns` is everything before that point: the build, its own deterministic `tick(0)` included.
- `__clock.runWarns` is everything the running page said after it.
- `bootWarns` stays the whole buffer, for the probes that step the movement and read it afterwards on purpose.
- The readers that mean the boot read `buildWarns`: `prepPage` (the battery's boot gate and every point and probe
  that prepares a page), `ci-battery`'s spec boots, the native host, and `probe-338-native-boot`.

That probe now raises a warn after the build and requires it in `runWarns` and absent from `buildWarns`, for both
specs. It reports any warn the running page raised on its own, rather than gating it. Its native control still sees
the engine-`Math` boot warn, so a build warning is still gated.

### Landing 6: the second primitive, the boolean intersection

3. only for a corner lying exactly on the other's plane, or a degenerate triangle, the exact distance is 0.

the distance (`begin_query`).

### Landing 9: a morphing mesh's tree is refitted, not rebuilt

**Why.** With both primitives exact, landing 0's profiler (`probe-338-check-profile.mjs`, the same eight heavy tasks,
browser, 198 s sampled) put the exact query at 53.2% and, inside it, **building its trees at 27.5%**. The cache is per

the mainspring ribbon (1,924) winds. Traced natively, `inspection:wind` built the chain's tree 721 times, once a pose,
17.2 million triangles in all, and the ribbon's 482 times.

**What shipped.** A geometry of a FAMILY already built takes the family's tree shape and recomputes only what depends
on the positions: the triangles in tree order, every leaf's box from its triangles, every inner box as the union of its
children's, in one descending pass (children are numbered after their parent).
- **What a family is.** The same vertex count, and the same SET of vertex triples, each of the family's found exactly
  once in the new geometry. An order-independent hash only finds the candidate; the membership is checked triple by
  triple, and any miss is a fresh build.
- **Why a set, not the index.** three-mesh-bvh's `computeBoundsTree` reorders a geometry's index triples in place.

  written matched nothing. The first build of this landing did that, and refitted 5,493 trees while still building
  the chain's every pose (the native wall moved 239 s → 238 s). A reorder moves whole triples and never renumbers a
  vertex, so the triple names the triangle.
- **Why the answers cannot move.** The union of exact boxes is the exact box of the subtree, so every box is the one a
  pass over the same triangles computes; only the tree's SHAPE is the family's rather than a fresh median split. No
  answer depends on the shape: a pair is pruned only when its bound clears the best by `PRUNE_PAD`, so the distance is
  the exact minimum over every pair under the bound, and the meet is true exactly when some pair meets. The compiled
  kernel still builds every geometry fresh, and shadow holds the two `Object.is`.

**What shipped.** The same algorithm, rewritten, built at `-std=c++23` by the same pinned zig 0.13.0 clang 18.1.6 with
every other flag unchanged:
- **Values, not pointers.** `Vec3` and `Box` are values with `constexpr` operators. Each operator is exactly the
  scalar expression the C++17 kernel wrote out per component, so `a + ab * (d1 / (d1 - d3))` computes what the three
  lines it replaces computed, in the same order. Its subscript `v[a]` is one deducing-`this` overload (C++23) serving
  both the const and the mutable view.
- **Triangles read as the maths names them.** A tree-order triangle array is a view read `tri[t, c]` (a corner) or
  `tri[t, c, a]` (a coordinate), C++23's multidimensional subscript, in place of `9 * t + 3 * c + a`. That offset is
  where a port slip would hide, and it is now written once.
- **The geometry checks itself as it compiles.** Every triangle primitive (`point_seg2`, `point_tri2`, `seg_seg2`,
  `seg_pierces`, `tri_tri2`, `tri_meets`, `box_dist2`, `pad2`) is `constexpr`, and G3's analytic pairs are
  `static_assert`s on them: parallel faces, a vertex over a face, skew edges, an edge piercing a face (both ways round),
  coplanar overlap, coplanar apart, a shared corner, and a triangle crossing the plane beside the face. Their
  coordinates are binary fractions, so the answers are exact and the asserts compare with `==`. `PRUNE_PAD`'s
  derivation (ten roundings at the movement's scale) is a `static_assert` too.
- **`if consteval`** gives the one function a constant expression cannot reach, `sqrt` (`__builtin_sqrt` is not
  `constexpr` in clang 18), a compile-time body: Newton's iteration, used by the asserts only on perfect squares,
  where it is exact. At run time it is `f64.sqrt`, as before.
- **`[[nodiscard]]`** on every primitive and query helper (24 sites; the arena helpers and the exports are left bare). The leaf loops are one template taking the pair test as
  a lambda, so the distance and the meet descents share it rather than each counting offsets.
- **Language features only, no headers.** zig's `wasm32-freestanding` under `-nostdlib` gives no libc++ include path,
  so the plan's option (a) held. Not used, and not needed: concepts (no template here has more than one caller's
  type), `uz` and `auto(x)` (no size arithmetic or decay-copy survived the rewrite), `std::bit_cast` (nothing inspects
  a double's bits).

**And the asserts are a live gate.** `kernel-build.mjs` now compiles a MUTANT on every run: the source with the
edge–face pierce test cut out (every edge then misses every face). It requires the compiler to refuse it on the
`dist(T0, SPIKE) == 0` assert, and it fails the build if the mutation site is missing or the mutant compiles. Measured
by hand before the control was written: cutting the pierce test, or answering 0 in the point–triangle vertex region,
fails the build; widening that region's test passes it, because no analytic pair puts a point there. The asserts are
a tripwire, and G3's random tiers remain the full check.

**What may not move, measured.**
- **The answers.** On the same tree (`main` at the branch point), the C++23 module's native wasm report is
  leaf-identical to the C++17 module's: 186,708 leaves under `report-diff`, 0 differences. The branch's js and shadow
  reports are leaf-identical to its wasm report. Shadow: 867,890 distance and 186,583 intersection calls, 0 differing
  (the same counts as landing 9's). 8,000 random queries (distance at three bounds and the meet, a fifth of the maps
  sheared) answer `Object.is` across the C++17 module, the C++23 module and the JS port. G3 passes every tier.
- **Reproducibility.** `kernel-build --check` reproduces the new module byte for byte (17,621 bytes, sha256
  `576972a6…`; it was 15,171). The growth is inlining: 17 functions where there were 18, and the two largest bodies
  are 3,898 and 2,822 bytes where they were 2,294 and 2,098, as clang now sees the leaf tests and the value operators
  whole. The x64 and arm64 rebuilds are the `native-host` legs' check, as before.
- **An ordinary clang.** The distro's clang 18.1.3 (`--target=wasm32-unknown-unknown`, the same flags, its own
  `wasm-ld`) builds the source too: different bytes (17,702, imports none), and the same answers, `Object.is` the
  pinned module's on the 8,000 queries. So C++23 sets the floor at clang 18 and does not bind the kernel to zig.

**Measured** (native, 4 workers, this container, the same tree):

| | C++17 wasm | C++23 wasm | C++23 js |
|---|---|---|---|
| **wall** | **223 s** | **224 s** | **223 s** |

No speed was sought and none moved: the 8,000-query bench reads the two modules within its own call-order bias (each is
faster when run first).

**Not done.** The compiled kernel still builds every morphing geometry fresh (landing 9's "not done"). Concepts, `uz`
and `auto(x)` were measured available and are unused because nothing here needs them; a later landing that adds a
second element type or size arithmetic is where they would earn their place.

### Landing 11: a compiled refit, measured and refused

**Why.** Landing 9 refitted a morphing mesh's tree in the js body, and wasm still built every new geometry fresh, the
chain once a pose. The owner asked for the same refit in the compiled kernel.

**What was built, and measured.** `geom_refit` kept the family's tree shape and read the new positions through the
founder's tree-order vertex indices (`sidx`), recomputing the boxes in landing 9's descending pass. Both kernels named
families through exact-mesh's `tripleKeys`. It was correct throughout: the native js, wasm and shadow reports were
leaf-identical to `main`'s (186,708 leaves), and shadow differed 0 times in 1,054,456 calls. Its speed was the problem:
- **The JS membership check cost more than the build it saved.** Checked in JS over two `Set`s, `inspection:wind` in
  one process walled 35.8 s against `main`'s 30.6 s (`familyMatch` alone 6.5% of the samples). A compiled build is
  cheap; the js body's refit paid because a JS build is not.
- **Moved into the kernel** (an open-addressed table of the founder's triples, one stamp per slot), the one-process
  slice was 28.9–30.3 s against 30.0–31.0 s, and every `inspection` axis summed to 71.8 s against 73.2 s.
- **But the battery runs four workers, and there it lost.** The native wasm battery walled 229–245 s against `main`'s
  215–224 s over three pairs of runs, `inspection` 229–243 s against 171–179 s. Four concurrent copies of the
  one-process axis script reproduced it (110–114 s against 100–104 s; refit switched off, 103–106 s), most of it on
  `reserve` (6.7 s → 17.1 s), which winds the mainspring ribbon.
- **Three corrections did not recover it.** Building a family's table only when a second geometry arrived, skipping
  the membership check entirely (an unsafe test build), and re-founding a family once its tree's spread (every node's
  half-perimeter) grew past 1.25× its founder's: 107–114 s each. Re-founding every 8th member brought `wind` under
  `main` (26–28 s against 28.4 s) but not the total. The refit's work and answers were the same as a fresh tree's
  (triangle pairs tested within 0.8%), so the residue is how it touches memory under contention: a member reads its
  founder's indices and layout from far back in the arena, where a build reads only what it has just been handed.
  That was not pinned down further.

So the compiled kernel builds fresh, as before, and the refit stays the js body's alone.

**What the work left behind.** G3's refit tier is stronger for the js refit:
- **The meets are both true and false.** The morphs are placed from overlapping to clear apart (127 meet of 300);
  before, every one met, and the meet half could not fail.
- **The refusal path is held.** A geometry built to COLLIDE with a family's candidate key (the counts and the hash
  unchanged, two triples replaced: the hash is a sum of invertible 32-bit mixes, so the collision is constructed)
  must be refused by the port's triple-by-triple check and built fresh, answering `Object.is` the kernel. No run had
  reached that path: every battery refuses 0. Building it found a defect in the compiled refit's draft, a refused
  offer counted and never built, which no battery had exercised.

**Does bit-for-bit compatibility hold the kernel back?** The owner's question, answered on a replay of 134,650 real
queries (the `beat`, `train` and `position` axes of `inspection`, captured with their 1,135 geometries) against the
kernel built under each flag set, every answer compared with `Object.is` to the shipped build's:

| build | queries, best of 3 | answers differing |
|---|---|---|
| shipped: `-O2 -ffp-contract=off -fno-fast-math -mno-simd128` | 2,504 ms | — |
| `-O3` | 2,275 ms | 0 |
| `-O3 -msimd128` (no fast-math) | 1,555 ms | 0 |
| `-O3 -ffast-math` | 2,965 ms | 0 |
| `-O3 -ffast-math -msimd128` | 2,898 ms | 0 |
| the same with `-mrelaxed-simd -ffp-contract=fast` (FMA) | 2,559 ms | 0 |

No. The relaxations bit-identity forbids (reassociation, reciprocal approximations, fused multiply-add) are slower
or no faster here; scalar wasm has no FMA instruction at all, so `-ffp-contract=off` costs nothing. The one real
speedup, SIMD128, is 1.6× on the queries and keeps every bit, because non-relaxed wasm SIMD is IEEE per lane and,
without fast-math, the autovectorizer cannot reassociate. Landing 5's `-mno-simd128` ("plain SIMD128 may come later")
was a precaution, not a cost of the contract. The ceiling on any kernel speedup is its share of the battery: shadow
timed wasm at 147 s of 628 s of check time, about 23%. Tried whole (not shipped here): the native wasm battery with the
kernel built `-O3 -msimd128` walled 206 s against `main`'s 215–224 s, its report leaf-identical to `main`'s (186,708
leaves) and G3 passing. Shipping it is its own landing: the module's bytes change, and `kernel-build --check` must
reproduce them on x64 and arm64.

### Landing 12: the native sweep engine, first check `inspection`

**Why.** Landing 11 showed the kernel is about 23% of the battery's check time; the rest is JS (posing, the checks'
loops, the deterministic maths). The owner asked for a totally native battery using the standard library, and chose,
of three scopes, a NATIVE SWEEP ENGINE: JS builds and poses the movement, and native code runs the sweeps over that
state. The other two were a native kernel addon (capped near 23%) and porting the whole battery (months, and a second
copy of every geometric law).

**What shipped.** JS supplies the posed state; native code supplies the queries.
- **`exportInspectionState`** (`src/inspect.js`, beside `runInspection`, sharing its units, pair tables, canonical
  axis entry and pose loop) hands a sink, per pose, the unit boxes and every CHANGED mesh's state: its own geometry
  and world matrix (what the meet reads), its `rigidFrame` view geometry and frame (what the running fit reads),
  whether that frame is rigid, and its world box. A mesh is unchanged when its geometry (identity, both attribute
  versions) and world matrix (`Object.is`, element for element) are; a mesh with children always re-sends, because
  `setFromObject` takes them in. Nothing three.js computes is ported.
- **`runInspection`'s tail is `inspectionPayload`**, so the JS sweep and the engine's findings assemble through one
  function.
- **`tools/native-sweep/sweep.cpp`** is C++23 with the standard library. It reads the stream, runs `runInspection`'s
  pair loop and `unitsIntersect` (first contacting mesh pair wins), and keeps the census as the JS memo's replay
  counts it (logical queries). It ports, operation for operation and cited at each site, three.js' `Matrix4.invert`
  and `multiplyMatrices`, `boxDistance` through det-math's three-argument `hypot`, and `meshesIntersect`'s two
  questions. The `boxesCanTouch` gate has an exact shortcut: det-math's `hypot` is never below its largest argument,
  so a gap over the threshold on one axis answers it alone.
- **Its queries are `tools/kernel/kernel.cpp` itself**, compiled for the host. A portability layer makes an address
  an offset into a block the host binds (`kernel_bind`) and growing memory a capacity check; the wasm module's bytes
  are unchanged (`576972a6…`).
- **The static-pair memo is the JS rule**: an answer is reused while both meshes' states are bit for bit the ones it
  ran on. The first engine bumped a mesh's version on every send, so the always-re-sent nested meshes never hit, and
  `beat` took 4.5 s in the engine alone; comparing the state instead took it to 0.77 s.
- **Built by `tools/native-sweep/build.mjs`** with the kernel's pinned zig (its bundled libc++), `-ffp-contract=off`,
  no fast-math, and `-mcpu=baseline`: zig otherwise targets the BUILD machine's CPU, which valgrind on the same host
  refused (an illegal instruction), and which would make the binary a property of its runner. The binary is never
  committed.
- **`tools/native-sweep/run.mjs`** boots, spawns the engine and streams into it (each geometry once, on first sight
  of its identity and versions), and `probe.mjs` is the acceptance.

| wall | 117.0 s | 20.1 s |
| payload | — | leaf-identical, 163,466 leaves, census included |

`probe.mjs` holds it: both ways on the same boot, `report-diff` leaf for leaf; its control hands the engine a contact
threshold of 0.05 for 1e-4 on one axis and requires a different payload (278 leaves on `beat`). CI runs it on x64 and
arm64 (`native-host.yml`, `native-sweep`), and `native-sweep-cross-arch` holds the two architectures' native payloads
leaf for leaf.

**Then `clearances`, where the engine DRIVES.** Its sweep visits a pose set that depends on its own answers (a coarse pass
every four poses, then the skipped poses beside any coarse sample within the band of the pair's per-axis minimum), so
streaming the poses in order cannot serve it. The engine runs `sweepClearances`' algorithm itself, ported step for
step, and asks JS for each pose it visits, in exactly the order the JS sweep sets them, so even a path-dependent mesh
(the chain re-tessellates lazily) sees the same history. JS answers through the same poser, now `sweepPoser` (the one
`exportInspectionState` runs on).
- **The one question JS keeps.** `meshClearance` asks `sampledVerdict` (a three-mesh-bvh parity raycast with its measured
  grazing behaviour) whether a body sits inside another wherever 0 < d < 0.05. Porting it bit for bit would mean
  porting the library's quirks, so the engine ASKS: it writes the two meshes and the bound, and JS, standing at that
  very pose, answers with the code the JS sweep runs.
- **The rest is ported**: `unitClearance`'s AABB gate (`boxDistance ≥ best`, with the same exact shortcut), the
  per-bound static-pair memo (exact replay, its census replayed), the outcome buckets, and the per-pair state.
  `checkClearances` is split into `clearancesSetup` (the §152 restriction, TODO 298's stand-downs, the pairs) and
  `clearancesPayload`, which both sweeps assemble through.

| all 17 axes, one process | JS `checkClearances` | native engine |
|---|---|---|
| wall | 22.7 s | 20.0 s |
| payload | — | leaf-identical, 211 leaves |

The queries were never this check's cost: every pose of every axis qualified for refinement, so it visits all 2,436,
and posing them (`setPose`, the boxes, the rigid views, the encoding: about 8 ms a pose) is most of either wall.

The shipped budgets never come within 0.05, so the witness is asked 0 times on them, and a probe of them alone would
leave the question path unexercised. `probe.mjs` therefore adds a control: every EXPECTED contact pair `inspection`
found, as a budget, on one axis. On `beat` that asks the witness 112 times (875 logical calls, the JS census's 875), and
the payloads agree leaf for leaf, violations included.

**Then `expectedContacts`, on the same driven sweep.** It is `sweepClearances` again; what differs is each row's PAIR:
its two mesh lists (a unit's meshes, or each unit's own metal where the row says `ownMetal`) and an exclusion rule (the
row's declared contacts, its `only:` siblings, the meshes two nested units share). Both read names and identities, never
a pose, so JS resolves each pair once, at setup, into mesh indices and the list of excluded mesh pairs, and the engine
skips those before counting anything, where `unitClearance`'s `exclude` skipped them. `checkExpectedContacts` splits
like `checkClearances` (`expectedContactsSetup`, `expectedContactsPayload`), and one driver core serves both.

**And `undeclaredClearance`, whose prune stays in JS.** Its loop is its own: every pose of every axis, the pair
complement of everything declared plus the two controls, its own world boxes (each geometry's cached `boundingBox`
under the world matrix, which the poser now sends beside `setFromObject`'s, with the geometry's JS `id` and position
version), unit-group boxes as three.js' `Box3.union` builds them (`Math.min`/`Math.max`, −0 and NaN as ECMA-262 has
them), and a memo whose HITS it counts, so the engine reproduces exactly when JS hits (its snapshot rule: the
geometry's `id`, its position version, the matrix compared with `!==`). Before an exact distance it asks three-mesh-bvh
whether the larger mesh's tree reaches the smaller one's box grown by the bound (`intersectsBox`), and that prune
decides what is measured, so it stays JS's, as `sampledVerdict` does. It is asked in ONE BATCH per pose: which mesh
pairs reach it is fixed before any distance (the gates read a fixed bound, the memo reads versions), so the engine
finds them in a first pass, in the JS loop's order, asks (`Q`), and then runs the loop with the answers.
`meshWorldBox` and `undeclaredPrune` are now the check's own helpers, called by both sweeps, so neither law is
written twice; the refactored JS check's payload is leaf-identical to its own before the split.

is now most of each native wall, and each check poses the whole net itself; one posing pass serving several checks is
the next saving, once the chain's path-dependence is measured rather than assumed.
