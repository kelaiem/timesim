## §338 — A native battery: one deterministic library, WebAssembly kernels, identical results on ARM and x86 — PARTIAL: landing 0's check profile, landing 1 (the native host) and landing 2 (deterministic maths) shipped

Proposed 2026-11-07 by the owner: a battery that is not platform or runtime dependent, gives identical results on ARM
and x86, is optimized for runtime efficiency, and targets WebAssembly. The design (one JS library of the build and the
checks, a compiled C++ kernel to wasm for the collision queries, hosts around it, and a byte-identical report across
architectures and engines as the gate) is the roadmap entry. This file records what has shipped.

### Landing 0, in part: where the check time goes, by function

`tools/probe-338-check-profile.mjs` boots the way the battery does (`virginBoot` + `prepPage`) and runs named tasks (a
check, or a §127 `check:axis` slice) under a CDP sampling profile started after boot: time by source file, the top
functions by self and by inclusive time, and a `.cpuprofile` per task. Nothing had profiled the CHECK phase by function:
§108's census times tiers, and §239's profile is the boot.

Eight heavy tasks (the heaviest slice of each sliced sweep, plus `sweptOverlap`, `penetration`, `plateSeats`,
`intraUnit`; about 40% of the `COSTS` column), dev container, 4 vCPU, 1 ms sampling, 380.5 s sampled, full coverage:

| inclusive, all eight | share |
|---|---|
| BVH closest-point query (`closestPointToGeometry`) | 55.3% |
| boolean triangle–triangle intersection (`intersectsGeometry`) | 22.4% |
| BVH construction (`MeshBVH`) | 5.5% |
| `sampledVerdict` | 4.0% |
| `setPose` | 3.4% |
| `updateMatrixWorld` | 1.5% |
| parity raycast | 1.2% |

The hottest leaves are three-mesh-bvh's segment–segment distance (22.6% together), three's
`Triangle.closestPointToPoint` (11.9%), `distanceToBox` (7.8%) and the separating-axis triangle's setup (5.8%).
`inspect.js` is 2–16% of a task. So the kernel's first primitive is the BVH-vs-BVH closest-point query, its second the
boolean intersection, and the two with BVH construction are the 83% a compiled kernel can address.

### Landing 1: the native host

**The plan was to cut a `src/movement.js` out of `main.js`. The measurement made that unnecessary for this landing,
and the landing is smaller and safer for it.** Booting `main.js` UNCHANGED in Node with crude page stand-ins, the
first thing that broke was line 48,774 of 66,104: the service-worker registration, after every part is cut. The
build region's browser references are about two. So the host answers the page's questions and the build runs as
written; `main.js` is not touched, so its browser build cannot have moved.

**What shipped.**

- `src/spec-fields.js`: the §22/§161 spec roster (`SPEC_FIELDS`) with `readSpec` and `publishSpec`, moved out of
  index.html's inline classic script, the one host fact the build needs and the one place a non-page host could not
  read. `src/spec-boot.js` publishes it for the page and is the entry module's FIRST import (dependencies evaluate in
  import order, so `layout.js`, which reads `__WATCH_SPEC` at import time, still sees it). It is a NAMED import on
  purpose: `tools/stamp-release.mjs` versions `from '…'` and `import('…')` specifiers and would ship a bare
  `import '…'` unstamped. `publishSpec` was held equal to the inline script's globals on four queries (none, two
  numbers, every string-parsed knob at once, an unknown key).
- `tools/native/`: `host.mjs` (`installHost`/`bootNative`: the DOM as one forgiving element, the battery's loopback
  origin so `state.js` takes `virginBoot`'s 404 `/__state` path, `fetch` answering 404 for `/__state` and
  `version.json` and THROWING for anything else, no animation frames, the spec through `publishSpec`, and a `touched`
  count of every stand-in a boot exercised), `three-headless.mjs` (the vendored three with a renderer and a PMREM
  that draw nothing), `loader.mjs`, and `boot.mjs` (boot one spec, print its wall, warnings, stand-ins and
  fingerprint). The host lives under `tools/`, so the app stays dependency-free and the payload does not carry it.
- `tools/probe-338-native-boot.mjs` and `.github/workflows/native-host.yml`: Chromium and native boots of the identity
  and `arrangement=designed`, in parallel (~75 s).

**Measured (the probe, this container: Node 22.23.4 / V8 12.4 against Chrome for Testing 153 / V8 15.3).**

| | identity | `arrangement=designed` |
|---|---|---|
| boots silent, both hosts | yes | yes |
| one roster (33 keys) and one parsed spec | yes | yes |
| §52 fingerprint | 556372915 = 556372915 | 512616833 = 512616833 |
| §152 PLACE digest, 66 units × 52 poses | identical | identical |
| §152 SHAPE digest | 27 of 66 differ | 27 of 66 differ |

The control holds: the native identity build's fingerprint differs from Chromium's designed build, so the comparison
can fail and the spec reaches each build. A native boot takes ~27 s here.

**SHAPE is reported, not gated, and the reason is the landing's main finding.** Each differing unit is classified at
the digest poses:

- *index-order* (15 units): positions and the triangle SET agree; only the index buffer's order differs. The page's
  first frames build bounds trees (103 on the identity build), and three-mesh-bvh reorders a geometry's index in
  place. So §152's SHAPE digest, which hashes the live index, is a function of what the page did after boot as well
  as of the metal. It reproduces across two browser boots (§152's gate) because both run the same frames.
- *positions* (11): the same vertex count, a few coordinates differing by ~1e-17, values near zero from a
  transcendental.
- *topology* (1 on identity, 3 on designed): a mesh's VERTEX COUNT differs: `Alarm winding arrest` mesh #24, 31090
  in Chromium against 31102 native; on the designed build also `Alarm release crank` and `Dial` mesh #176, 554
  against 548. A construction decision flips on a last-ulp difference. The fingerprint, which reads quantized boxes,
  cannot see it.

The cause of the last two classes is the ENGINE, not the host. On 20,000 inputs, V8 12.4 and V8 15.3 disagree by 1 ulp
on 2–11% of inputs for every transcendental (`sin`, `cos`, `tan`, `atan`, `atan2`, `exp`, `log`, `pow`, `**`, `cbrt`,
…); `hypot` agrees between the two V8s and not with JavaScriptCore; only `sqrt`, which IEEE 754 requires to be
correctly rounded, agrees everywhere. V8 15.3 is much closer to
JavaScriptCore (Bun 1.4.4) than to V8 12.4, so V8 changed its maths library between those versions. "The same engine
gives the same results" is therefore false across engine VERSIONS, which is also what the `ci-env-upgrade` skill's
"same source builds different metal on a new browser" describes. A report leaf-identical between the hosts (§338's
G2) cannot hold until the build's arithmetic stops depending on the engine's libm: §338's deterministic-math landing
now comes before the native runner's parity gate, not after it.

**Not done in landing 1, and filed in the entry:** deterministic maths, the canonical SHAPE digest and the ARM legs
(landing 2, below), the native battery runner, and the wasm kernel.

### Landing 2: deterministic maths

**The goal: the same metal from the same source on every engine and CPU.** ECMA-262 leaves every transcendental
`Math` function "implementation-approximated", and landing 1 measured what that costs. The fix is to stop asking
the engine.

**What shipped.**

- `vendor/det-math.module.js` and `vendor/LICENSE-stdlib.txt`, GENERATED by `tools/det-math-vendor.mjs` from exactly
  pinned stdlib-js packages (pure-JavaScript ports of FreeBSD msun / Sun fdlibm, Apache-2.0, the Sun notices kept)
  bundled by a pinned esbuild. `--check` rebuilds it in a temporary directory and compares bytes: 201,748 of them,
  reproduced. The tool asserts the bundle calls no `Math` builtin but the exact ones (`abs`, `ceil`, `floor`, `round`,
  `sqrt`) and uses no `**`. Measured before choosing it: on 40,000 inputs per function, its results are bit-identical
  in V8 12.4, V8 15.3 and JavaScriptCore; it is within 2 ulp of V8's own; and it costs 1.05–2.2× a builtin call
  (`sin` 1.84×, `cos` 1.08×, `atan2` 1.05×, `pow` 2.22×), which the boot does not notice (native boot 25.5 s against
  27–28 s before).
- `src/det-math.js`: `installDetMath` replaces the 22 implementation-approximated functions (`sin` … `atanh`, `pow`,
  `hypot`) on `Math`. The exact ones stay the engine's, because IEEE 754 or ECMA-262 already fixes every bit of them.
  Two functions are written here rather than taken from stdlib:
  - **`pow` applies ECMA-262's Number::exponentiate itself** and gives stdlib only a finite positive base. Measured,
    stdlib follows C at the special values and is wrong at several: `pow(NaN, 0)` gives NaN (JS requires 1),
    `pow(±1, ±Infinity)` gives 1 (JS requires NaN), the ±0 and −Infinity bases are off, and its odd-integer test reads
    `y − 1`, so `pow(-1, 1e300)` gave −1.
  - **`hypot`** is ECMA-262's variadic function, computed as m·√Σ(xᵢ/m)², each operation correctly rounded.

  Every special value now matches the engine's, which the spec pins down. What is left is accuracy at the extremes,
  where the true value lies next to a boundary: `exp(-745)` underflows one subnormal early, `cosh(710)` overflows,
  and `pow` differs by 1 ulp near 1. All of it is deterministic, and none of it is in the build's domain.
- `src/det-math-boot.js` installs it and checks its KNOWN ANSWERS: per function, a hash of the result bits (NaN made
  one pattern) over a fixed input set, recorded in `src/det-math-kat.js` by `tools/det-math-kat.mjs`. It is
  **index.html's first import**, so every later module, three.js included, computes with it. The native host imports
  it before `main.js`. `main.js` re-says its findings as boot warnings (rule 6), and warns when no host installed it.
- **The `**` operator** cannot be reached by replacing `Math.pow`, so the build no longer uses it.
  `tools/check-det-math.mjs --fix` rewrote 313 sites on index.html's module graph, re-run after rebasing onto #921 (228 in `main.js`, and the 2 in
#921's new `src/ribbon-solve.js`, which the lint found the day it joined the graph) from the
  AST as `Math.pow`. Without `--fix` it gates:
  - the graph free of `**`, except two named vendored sites that are exact (`Infinity ** 2`, `2 ** 16`); an allowed
    site that disappears is stale and fails;
  - the bundle's audit;
  - the entry's first import;
  - the full known answers.

  Its controls plant a `**` and a `Math.sin` and require both to be seen.
- **§152's SHAPE digest hashes the index as a triangle SET** (`indexSetHash`: each triangle rotated to its smallest
  index, which keeps its winding, then hashed; per-triangle hashes summed under two mixes). Landing 1 found that the
  page's first frames build bounds trees that permute index buffers in place, so the key carried which trees had been
  built. This changes every stored key once, which sends the next incremental run whole: the safe direction.
- **`native-host.yml` is the portability gate**, in three jobs:
  - `maths`: the vendored bytes, the lint, and the known answers on Node (V8) and Bun (JavaScriptCore);
  - `native-host`: the probe on `ubuntu-latest` (x64) AND `ubuntu-24.04-arm` (arm64), SHAPE gated, each writing its
    digests;
  - `cross-arch`: `tools/compare-338-hosts.mjs`, every build on both machines one movement, unit digest for unit
    digest, with a control.
- The deploys assert `LICENSE-stdlib.txt` beside the bundle, and `tools/` gains one pinned package (`acorn`, the
  parser the lint and the codemod use).

**Measured (`tools/probe-338-native-boot.mjs`, this container: Node 22.23.4 / V8 12.4 against Chrome 153 / V8 15.3).**

| | landing 1 | landing 2 |
|---|---|---|
| fingerprint, identity / designed | equal | equal (556372915 / 512616833 on landing 1's base, unchanged by the maths; 594372214 / 1098600512 on the rebased tree, which carries #921's spring re-solve) |
| PLACE, 66 units × 52 poses | equal, until #921's tree straddled one cell edge (below) | the hash itself equal; 0 straddles |
| SHAPE differing, identity | 27 (index-order 15, positions 11, topology 1) | **0** |
| SHAPE differing, designed | 27 (14 / 10 / 3) | **0** |
| known answers, both hosts | — | reproduce (256 inputs × 22 functions at boot) |

With deterministic maths alone the positions and topology classes vanished (18 units then differed by index order
only); the set hash took those. **And the one PLACE straddle closes.** On #921's tree, with the engines' own maths, the Balance at one digest pose
(`{tau 0.13, …, maintHold 0.5}`, where the posed hold's advance lands on an escape step) parted 2.6e-12 s in τ and
1.28e-9 in metal across a 1e-6 cell edge, and #921 (304b3258) made the PLACE gate the cell itself, with controls.
With deterministic maths, re-measured on the rebased tree, that pose's hash is EQUAL in both hosts and the straddle
report reads 0 on both specs. An ill-conditioned pose amplifies a difference, and with the arithmetic bit-identical
there is none to amplify. The cell comparison stays as #921 wrote it, as the backstop. The rule #921's session
proposed (keep the pose net off ill-conditioned instants) is filed in §338's entry as a guard for any host or
library re-record that is NOT bit-identical.

**The control bites**: the same native boot with the engine's own `Math` differs from
Chromium in SHAPE on 4 units (`Alarm release crank`, `Alarm release seat`, `Alarm winding arrest`, `Dial`; 5 on the
rebased tree), and it
warns at boot that deterministic maths is not installed. The known answers reproduce in Node and in Bun 1.4.4
(JavaScriptCore) at the full 20,023 inputs per function.

**The boot paid for it in one place, and §266's rule fixed it.** Boot-yield held the thread 848–903 ms (ceiling 550;
`main` 372). A seam-trace diff of two native boots, deterministic maths against the engine's, put the growth in two
stretches, both a single `makeBarrel` call: the going drum (seams 100→101, 310 → 602 ms) and the alarm barrel
(216→217, 382 → 1,074 ms). A CPU profile put 1,312 ms of those two calls' 1,671 in `pow`. `mainspringFrames`' k-solve
bisects a 128-panel length integral 44 times a frame, `Math.pow(a / A, k)` at a solved, non-integer `k`, and the
deterministic `pow` is about twice the engine's. So both became step generators (`makeBarrelSteps`,
`mainspringFramesSteps`, a yield per wind frame, per sensitivity sample and per tube), resumed from `main.js` under
two new seams. `boot-progress.js` was regenerated (`--write`, three boots). The steps are the same arithmetic in the
same order: the probe's digests before and after are identical, unit for unit. Boot-yield then held 239–280 ms (PASS,
both controls firing).

**Three generated tables are stale on `main` itself, and this landing leaves them so.** Measured on a clean worktree
of `main` (b2d7b7a1) and on this branch alike: `free-outline --check` reads `src/free-outlines.js` stale,
`gong-bench-data --check` reads `src/gong-bench-data.json` drifted, and `gong-seats --check` runs past 50 minutes with
every candidate refused (form cases 40.15–40.75 mm across, over the 40 mm cap). They predate this branch, and no CI
workflow gates them, so they are reported here rather than regenerated inside a maths landing.
`strike-keep-round --check` passes, and so does `validated-configs --check`.

**Not covered, said rather than implied.** Pages that do not import `det-math-boot.js` (technic, booklet, gong bench,
test-geometry, the explainer and the primer), Web Workers, and tools that call `src/` builders under
`tools/three-node-loader.mjs` still use the engine's `Math`. None of them feeds the battery. The battery's own Chromium
run builds with the new maths, so its baseline moves once with this landing, and that is the whole battery's to
judge. Five probes that read source text fail, on this branch and identically on a clean `main`
(`probe-219-catalogue`, `probe-337-geared-geneva`, `probe-161-lawed`, `probe-262-gong-note`,
`probe-l3-shaft-ld-filter`): they predate this landing.
