## §330 — Hosted pull requests take the push's four-way battery split

Out of the owner's ask (2026-11-03) to profile the hosted battery and then split a PR's run the way a push's is split.

### Why

A push to `main` has run as four parallel hosted jobs since §264/§265: the battery harness, `battery spec`, `battery points` and `battery probes`. A pull request ran every stage in ONE process. Measured on two hosted runs the same day:

| run | wall | runner time | what it spent |
|---|---|---|---|
| push `af560fd9` (four jobs) | 14.6 min | 43.8 runner-min | the harness's shards 9.9 min then 230 s idle waiting for the point tier (13.6 min, the critical path) |
| PR #866 (one job) | 33.8 min | 33.8 runner-min | shards 9.0, spec tier 7.7, point tier 10.5, probes 5.2, in series |

The PR's point tier was also CEILINGED to `POINT_PR_BUDGET_MS` (600 s), only to bound that one process's wall. On #866 the ceiling SKIPPED `designed` and `form-rect`, so the PR verified one point of three.

### What changed

- **The route** (`battery.yml`) sets `tiers_job` on a hosted, unsplit `pull_request` as it does on a push or a hosted dispatch, so the three sibling jobs run beside the battery from t=0.
- **The run mode** drops `--points-pr` and `--points-base` on that path: the point tier is the sibling's, swept FULL with no ceiling, the only kind `pointsRefusal` accepts. The PR's own shards stay incremental (`--baseline`, `--digests-base`) against its base's baseline, so a PR still sweeps only what it changed, and its point tier stops inheriting. The harness already refused `--tiers-from` beside `--points-pr`, so the two modes cannot mix silently.
- Nothing else moves: the fetchers, `acceptTiers`, the probes' gate on `battery` and the in-process fallback when a sibling dies are the push's own. The worst case is the PR as it was.

### Where it does not apply

- **The self-hosted host.** Three more jobs would take three more slots, which §260 keeps for the single process.
- **A matrix opt-in.** §259's workers already spread both tiers.
- **Every PR off the fan-out** keeps `--points-pr` and its ceiling.

### The costs, stated

- **Money:** none. The repository is public, and its hosted Linux minutes are not billed.
- **Runner time:** about +30% per run (the push measured 43.8 runner-min against the single process's 33.8). The extra is four jobs' setup (~25 s each), boots each job repeats, and the harness waiting on its slowest sibling.
- **Concurrency:** a PR holds four hosted jobs at once instead of one, so the account's concurrent-job limit is reached by a quarter as many simultaneous PR runs.

### Expected, and how to read it

A hosted PR should wall at about the push's ~15 min: its slowest sibling is the point tier, now with `form-rect` swept full. This is not yet measured on a PR. The first hosted PR after this lands is the measurement, and its route summary names the fan-out. Task 2 of the same session (the rectangular case's sliver triangles, which make `form-rect`'s sweep the critical path) is the next lever on that number.

From here hosted is the default and the host is a backup (CLAUDE.md, battery routing). Hosted runner speed varies (§263 measured a 1.77x spread across runners), so read these as a range, not a cap.
