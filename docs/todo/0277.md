## 277. probe-142-tour asserts the control panel is open after End, but it starts collapsed — CLOSED

Filed 2026-10-29, found while landing the reading-paced tour dwells (PR #833). Not
caused by it: the same single FAIL reads on a clean checkout of `main`, run in a
detached worktree.

**What fails.** `tools/probe-142-tour.mjs`, step 4, ends the run from the Tour
button's gate and then holds `#clock-ui`'s display to `!== 'none'`:

    FAIL the panel did not come back after End

Every other row of the probe is OK (22 of 23), so the probe exits 1 and its one
red row hides whatever the next change to the tour breaks.

**What is true.** The probe's expectation is stale, not the app. The main panel
(`#clock-ui`) boots COLLAPSED, and the tour's hide/restore pair gives back exactly
the state it found: `hidePanelForScript` hides a panel only if it was up and
records that it did, `restorePanelAfterScript` restores only what it hid (its own
comment: "a viewer who had collapsed one gets exactly that back"). Measured in
headless Chromium by reading `style.display` of the two panels around a tour,
1100 px wide:

| | `#clock-ui` | `#view-hud` |
|---|---|---|
| before the tour | `none` | shown |
| during | `none` | `none` |
| after `scriptStop()` | `none` | shown |

The panel was never open, so "back" is `none` and the app is right: the view HUD,
the one panel that was up, is the one that returns.

**The fix.** Make the probe assert what the code promises, read off the page and
not retyped: snapshot both panels' display before the tour starts, and after End
require each to equal its snapshot, with `#view-hud` shown among them so the row
still fails if the restore is ever lost. It needs a CONTROL for the same reason
every row here has one: open the panel first (`H`, or `setPanelHidden(false)`
through the page's own control), run the tour, and require the panel to be open
again after End. That control is the case the current row thought it was testing,
and it is the one that would catch a restore that stops working.

**Closed 2026-10-29.** The End row now snapshots both panels before the run and
requires them equal after End, with a precondition that the view HUD started up so
the row cannot pass vacuously, and the control the item asked for opens the panel
first and requires it open again after End. A mutation check backs them: with
`restorePanelAfterScript` made a no-op in a scratch copy, both rows go red (the HUD
`""` before and `"none"` after, and the open panel not coming back), and the
unmutated probe is 23 OK, exit 0, on two runs in a row.

**What fixing it turned up, which the item did not predict.** The mutation run
also failed an unrelated row, "the run did not advance to stop 1", and so did a
clean run: a flake, in the probe's own advance step. A stop's dwell clock starts
only once the stop's actions have SETTLED (stop 0's crown eases in), and that
easing runs in the live frame loop. The advance helper ticked 200 times inside one
synchronous in-page loop, so no frame could run and, whenever the crown had not
settled before the call, the whole budget was spent before the clock started. It
passed in one run and failed in the next. Ticks now go in 0.5 s chunks with a pause
between them for the frames. Worth carrying forward: a probe that drives
`scriptTick` is driving only HALF of what gates a stop, and a loop that never
yields the page cannot move the other half.
